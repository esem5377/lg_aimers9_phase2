# v10 — 상황 기반 구종 확률 피처(sit_*), 리더보드 906점으로 하락 → 기각 (2026-08-17)

v9_timesplit(909→924점, 시간 기반 검증)에 **trackman_history.csv 기반 "상황별 구종
확률" 피처**를 추가해봤으나, 실제 리더보드에서 **924 → 906으로 하락**해 최종
기각. 다만 그 과정에서 검증 방법론 버그 2건과 KBO 데이터 자체의 레짐 변화를
발견해서 기록으로 남긴다.

## 아이디어

trackman_history.csv를 `pitcher_id`로 조인하는 건 이미 불가능하다고 확인됐지만
(overlap 0), train과 trackman이 공유하는 **상황 컬럼**(`balls_before`,
`strikes_before`, `outs_before`, `pitcher_hand`, `batter_hand`)을 기준으로
population-level 구종 비율(`sit_fastball_rate`, `sit_breaking_rate`,
`sit_offspeed_rate`, `sit_n`)을 집계해 lookup 피처로 붙이면 어떨까 하는
아이디어. 개별 투구를 재식별하지 않는 안전한 방식.

주의: train의 `pitcher_hand`/`batter_hand`는 `1`/`2`로 익명화, trackman은
`Left`/`Right` 문자열이라 공식 매핑이 없음. 두 데이터의 비율(투수 기준 약
74~75%, 타자 기준 약 52~54%가 서로 대응)을 비교해 `1=Left, 2=Right`로
역추정해서 매핑함 (개별 선수 식별이 아니라 카테고리 라벨 복원이라 안전).

## 검증 과정에서 발견한 버그 2건

### 버그 1: 연도 단위 정보 누출 (해결)

처음(`train_v13_situational.py`, `train_v13b_...`) `sit_stats`를 만들 때
`trackman_history.csv` **전체(2019~2024)**를 그대로 썼다. 시간 기반 검증에서
2024를 검증할 때도 이 lookup에 **2024 자신의 패턴이 이미 포함**돼 있어
검증 점수가 부풀려짐. `train_v13c_situational_honest.py`에서
`season<=2023` trackman만 쓰도록 고쳐 재검증했는데, **개선폭이 줄기는커녕
비슷하거나 더 크게 나와서(+20~26)**, 이 leak이 실제 하락의 원인은 아니라고
결론.

### 버그 2 (진짜 원인은 아니었음): 2023 fold 조기종료

`train_v15_walkforward.py`로 2021/2022/2023/2024 각 연도를 검증년도로 둔
walk-forward 검증을 돌렸는데, val=2023 fold만 CatBoost가 `best_iteration=1~3`
에서 멈춰 BSS≈12(사실상 무의미)로 나옴. `early_stopping_rounds`를 50→150으로
늘려도 동일 — 즉 조기종료 민감도 문제가 아니라 **train(2019~2022)으로 2023을
예측하는 게 근본적으로 안 되는** 진짜 데이터 현상이었음.

## 진짜 원인: `game_type` F/R 관계의 2023년 역전

`game_type`(F/R 2종, F가 전체의 ~10%)별 제구성공률을 연도별로 보면:

| 시즌 | F | R |
|---|---|---|
| 2019 | 68.9% | 54.9% |
| 2020 | 58.8% | 52.7% |
| 2021 | 70.4% | 51.3% |
| 2022 | 70.9% | 50.4% |
| **2023** | **47.3%** | **50.3%** |
| 2024 | 45.9% | 49.0% |

2019~2022년 내내 "F면 제구성공률이 훨씬 높다"는 패턴이 4년 연속 일관됐는데,
**2023년부터 완전히 역전**돼 2024까지 유지됨. 2019~2022만 학습한 모델은 이
"F=고성공"이라는 강한(하지만 이제는 틀린) 규칙을 확신을 갖고 학습해 2023
예측이 근본적으로 실패한 것. 저희 파이프라인 버그가 아니라 **KBO 데이터
자체에 2023년경 실제 레짐 변화가 있었다**는 뜻이며, 시간 기반 검증(최근
연도 반영)의 필요성을 다시 한번 뒷받침하는 사례.

## 진짜 결론: sit_*는 학습 이력이 쌓일수록 효과가 사라짐

walk-forward 결과에서 2023 fold(양쪽 다 학습 실패라 무의미)를 빼고 보면:

| 검증년도 | train 연차 | sit_* delta |
|---|---|---|
| 2021 | 2년 | **+50.6** |
| 2022 | 3년 | **+13.6** |
| 2024 | 5년 | **-1.1** |

**학습 이력(연차)이 쌓일수록 sit_*의 이득이 계속 줄어들다 마이너스로
전환**됨. sit_*는 `asof_pitcher_*` 개인 이력이 얕을 때(학습 초반) 대체재
역할을 하지만, 이력이 충분히 쌓이면 오히려 노이즈가 됨. 실제 제출은
2019~2024 **6년치 전체**로 학습하는, 표에서 가장 이력이 많은 상황이라
sit_*가 도움되지 않는다는 예측과 실제 리더보드 결과(924→906)가 정확히
일치함.

## 산출물

- `train_v13_situational.py`: 초기 단일 실행 테스트 (2024 BSS 738.9, +1.4)

- `train_v14_timesplit_situational.py`: v9 구조에 sit_* 결합한 전체 파이프라인 검증 (2024 홀드아웃 블렌드 BSS 751.8)
- `train_v14_final.py` / `script_v14.py` / `build_submit_v14.py`: 실제 제출에 쓴 코드 (리더보드 906점)
- `train_v15_walkforward.py`: 2021~2024 walk-forward 검증 (leak 방지 assert 포함, 진짜 원인 규명)
- `model_v14/`: 실제 제출했던 모델 아티팩트
