### 5. 실험: 3-fold walk-forward CV로 재검증 — 채택할 개선 없음, 대신 중요한 발견
- 세션 여유 시간에 자동 탐색 진행: 단일 홀드아웃(2024) 기준 선택 편향 문제(섹션 2의 v5 실패 원인)를 줄이기 위해 `work/experiments/tune_cv_robust.py` 신규 작성. 3개 폴드(train≤2021→valid2022, train≤2022→valid2023, train≤2023→valid2024)로 재검증하면서 신규 후보 2개도 같이 테스트.
- **핵심 발견: 시즌 간 자연 변동폭이 압도적으로 큼.** 동일 모델(tuned_params)의 폴드별 AUC가 2022=0.5795 / 2023=0.5279 / 2024=0.5506로 0.05 이상 흔들림 — 지금까지 "의미 있다"고 판단해온 개선폭(±0.0003~0.0005)의 100배 수준. v5가 로컬에서만 좋고 리더보드에서 하락한 것도 이 맥락에서 재해석됨: 애초에 단일 시즌 검증 자체가 이 정도로 불안정했음.
- **baseline_params(최초 CatBoost 기본값, lr=0.03/depth=8/l2=3) vs tuned_params(v4 채택, trial 7)**: 평균 AUC 0.55243 → 0.55264(+0.00021)로 tuned가 근소 우위지만, **폴드 전체에서 일관되게 이기지는 못함**(2023 폴드는 baseline이 오히려 더 높음: 0.52801 vs 0.52786). "확실한 개선"이라기보단 "근소 우위+노이즈"에 가까움. 다만 리더보드 889점이 실측된 값이라 되돌릴 이유는 없어 v4 유지.
- **tuned + `max_ctr_complexity=6`** (CatBoost의 leak-safe ordered CTR 자동 카테고리 조합을 더 깊게 허용): 3개 폴드 전부 tuned_params와 **소수점까지 완전히 동일한 결과** — 범주형 7개짜리 저카디널리티 세팅에서는 기본값으로 이미 포화 상태라 완전 무효. **기각.**
- **tuned + 파생 피처 3종**(`ix_skill_diff`=asof_pitcher_success_rate−asof_batter_success_rate, `ix_count_pressure`=strikes_before−balls_before, `ix_risp`=RISP 여부 — 전부 train.csv 자체 컬럼의 단순 연산, 대회 규칙상 문제 없음): 평균 AUC 0.55194로 baseline보다도 낮음(-0.00050), 2023 폴드는 best_iteration=1로 사실상 즉시 과적합 감지. **기각.**
- **결론**: 이 피처셋 + CatBoost 조합은 사실상 노이즈 바닥(시즌 변동폭 대비 개선폭이 100배 작은 스케일)에 도달한 것으로 판단. 구조적으로 다른 접근(피처 소스 자체를 바꾸거나 검증 방법론을 바꾸는 것) 없이는 추가 미세조정의 기대 효율이 낮음. 프로덕션 파일 변경 없음(모든 후보 기각), `tune_cv_robust.py`는 향후 후보 검증용 재사용 도구로 보존.

- 처음엔 두 개를 동시에 백그라운드로 돌렸다가 CPU 코어(16개) 경합으로 load average 32까지 치솟아 15분 넘게 fold 0도 못 끝냄 — 둘 다 kill하고 순차 실행(v3 먼저, 끝나면 v4)으로 전환해서 정상 속도(코어당 최대 활용) 회복.
- **결과**:
  - v3(트랙맨만 수정, raw id 유지): AUC **0.57342**, logloss 0.68260 — 원본(0.5731) 대비 **+0.00032**
  - v4(raw id만 제거, 트랙맨 원본대로 깨짐): AUC **0.56997**, logloss 0.68338 — 원본 대비 **-0.00313**
  - → v2(둘 다, -0.0026)의 하락은 거의 전부 raw id 제거 쪽 효과(-0.0031)이고, 트랙맨 수정은 오히려 작지만 일관된 양의 효과(+0.0003~+0.0005, 두 세팅에서 같은 방향).
- **v3의 `meta_info.pkl`을 열어보다가 원본 코드 전체에 있던 버그 발견**: `train_p_col = [c for c in train_df.columns if 'pitcher' in c.lower()][0]`가 `pitcher_id`가 아니라 **`score_diff_pitcher_team`**(컬럼명에 'pitcher' 포함, train.csv에서 `pitcher_id`보다 앞에 위치, 고유값 52개의 점수차 컬럼)에 매칭됨. 즉 지금까지 "GroupKFold가 투수 단위로 분리한다"고 이해했던 게 **틀렸음** — 실제로는 점수차 구간으로 묶은 것이라 같은 투수의 행이 train/valid에 자유롭게 겹칠 수 있음. 원본 `jh_ws/train.py`(908/909점 낸 코드)에도 동일한 버그 존재, v2/v4는 raw id 제거 작업 중 `train_p_col = 'pitcher_id'`로 직접 지정해서 우연히 이 버그를 피함.
- **영향 재해석**: v4에서 raw id 제거가 손해로 나온 건, id가 "진짜 미관측 투수 일반화 신호"라서가 아니라 실제로는 같은 투수가 train/valid에 새는 구조에서 **암묵적 메모이제이션(8/15에 봤던 것과 같은 패턴)으로 이득을 보던 것**을 제거해서일 가능성이 높음. 다만 리더보드 909점은 이 버그와 무관하게 실측값이라 유효.
- **다음 액션**: `train_p_col`을 실제 `pitcher_id`로 고쳐서 "진짜" 투수 단위 group k-fold로 재검증 필요 — raw id의 진짜 일반화 효과를 확인하려면 이게 선행되어야 함.

### 9. 리더보드 제출 에러 발견 및 수정 — pandas 버전 호환성 문제 (앞으로 모든 제출에 적용할 교훈)
- 제출 결과: `TypeError: StringDtype.__init__() takes from 1 to 2 positional arguments but 3 were given (script.py:80)`.
- **원인**: 로컬 개발 환경 pandas가 3.0.5로 최신인데, pandas 3.0에서 텍스트 컬럼의 기본 dtype이 `object`에서 새로운 `StringDtype`으로 바뀜(PDEP-14 계열 변경). `trackman_context.pkl`이 pandas DataFrame을 그대로 joblib 피클한 파일이었고, 그 안의 `inning_state` 테이블 `top_bottom`('T'/'B') 컬럼이 이 새 `StringDtype`으로 저장됨. 평가 서버는 더 오래된 pandas를 쓰는 것으로 보이는데, 구버전 `StringDtype.__init__`은 신버전이 피클에 새겨넣은 생성자 인자 개수(3개)를 받지 못해 unpickle 시점에 에러. `meta_info.pkl`(순수 str/float/list/dict만 포함)과 fold 모델 pkl들(feature_names_in_이 numpy `<U36` — pandas dtype이 아니라 numpy dtype이라 버전 안전)은 확인해보니 문제 없었음 — `trackman_context.pkl`만 유일한 pandas DataFrame 피클이라 원인으로 특정.
- 참고로 같은 파일이 하루 전 `submit_v4_catboost.zip`(889점)에도 포함됐었는데 그땐 문제없이 통과했음 — 로컬 클린룸 테스트로는 이런 크로스 버전 unpickle 문제를 애초에 잡을 수 없다는 것도 확인(로컬은 저장·로드가 같은 pandas라 항상 통과함). 정확한 재발 조건(그땐 왜 됐는지)은 특정 못 함, 근본 원인(버전 의존적 피클)만 확실히 제거하는 방향으로 대응.
- **수정**: `trackman_context.pkl`(DataFrame 직접 피클) 대신 `trackman_context_safe.pkl`(각 그룹 테이블을 `to_dict(orient='records')`로 순수 파이썬 dict 리스트로 변환해 저장, `.item()`으로 numpy 스칼라도 파이썬 기본형으로 정리) 사용. `script.py`는 추론 시점에 `pd.DataFrame(records)`로 평가 서버 자체 pandas를 이용해 테이블을 새로 만든 뒤 병합 — 어떤 pandas 버전이 설치돼 있어도 그 버전이 스스로 dtype을 결정하므로 크로스 버전 문제가 원천 차단됨. 이 패턴은 jh 원본 코드가 트랙맨 데이터를 `trackman_records`(`to_dict(orient='records')`)로 저장했던 것과 동일 — 이미 실전에서 검증된 안전한 방식.
- 로컬 클린룸 재검증(예측값 동일) 통과 후 수정판 재전달, 리더보드 재제출 대기 중.
- **교훈**: 앞으로 joblib/pickle로 저장하는 모든 아티팩트에서 pandas DataFrame/Series/ExtensionDtype을 직접 피클하지 말 것 — 항상 `.to_dict()`/`.tolist()` 등으로 순수 파이썬 자료구조로 변환해 저장하고, 로드 시점에 재구성. 로컬 클린룸 테스트는 저장·로드 pandas 버전이 같아 이 클래스의 버그를 못 잡으므로, 이런 크로스 버전 리스크는 애초에 코드 패턴으로 예방해야 함.
- **수정판 제출 결과: 905점.** 원본(909점) 대비 **-4점** — 로컬 OOF에서 트랙맨 수정이 소폭 양(+0.0003)으로 나왔던 것과 반대로 실제 리더보드에서는 하락. 오늘 제출 기회 소진되어 추가 확인은 다음 기회로 미룸.
  - v3의 로컬 OOF 개선폭(+0.0003)이 애초에 저희 프로젝트 기준(0.0005 이하는 노이즈 의심)에 못 미치는 수준이었던 데다, section 8에서 발견한 `train_p_col` 버그(투수가 아니라 `score_diff_pitcher_team`으로 그룹핑)로 이 OOF 지표 자체의 신뢰도가 원래도 낮았던 상황 — 실측 결과가 그 불확실성을 확인해준 셈.
  - **현재 팀 전체 최고 버전은 다시 `jh_ws/submit_jh_ensemble.zip` (909점)로 확정.** `submit_jh_v3_trackmanfix.zip`(905점)은 기각, 참고용으로만 보존.
  - **다음 액션(제출 기회 재개 시)**: `train_p_col` 버그를 `pitcher_id`로 실제 고쳐서 "진짜" 투수 단위 group k-fold로 raw id 제거 효과를 재검증 — 지금까지의 v2/v3/v4 OOF 비교가 전부 잘못된 그룹핑 위에서 이뤄진 것이므로, 이 수정 없이는 로컬 지표를 신뢰하기 어려움. 제출권 없이도 로컬 OOF까지는 미리 돌려둘 수 있음.

### 12. 1100점 목표로 새 알고리즘(DeepFM류 임베딩) 시도 — 방향은 유효하나 아직 스케일 부족
- 팀원 목표: 909점에서 1100점(+191점, +21%)까지. 지금까지의 GBDT 피처/하이퍼파라미터 미세조정은 전부 exhaust된 상태라 다른 알고리즘 계열을 시도.
- **가설**: 기존 피처는 전부 단변량(투수 개인 성공률, 타자 개인 성공률)이고 "이 투수 vs 이 타자" 매치업 상호작용 피처가 아예 없음. GBDT는 792×830 조합을 raw id로 직접 스플릿하기엔 너무 희소해서 못 잡지만, FM(Factorization Machine)류 저차원 임베딩은 이런 상호작용을 효율적으로 학습 가능.
- **환경 준비**: `pip3 install torch --index-url .../cu121`로 PyTorch(CUDA) 설치(다운로드만 25분+, nvidia-*-cu12 의존성이 많아 용량 큼). GPU 확인: RTX 4060 Laptop 8GB, `nvidia-smi`로 정상 인식.
- **`jh_ws/deepfm.py`**: 임베딩(pitcher_id/batter_id/team/hand/top_bottom/game_type/base_state, dim=16) + FM 쌍별 상호작용(효율적 sum-square 공식) + Deep MLP(256→128→64) + 선형항, 진짜 group split(투수 단위)으로 학습.
  - 최초 시도(기본 임베딩 초기화, lr=1e-3): logloss가 1.3~3.0으로 폭주, AUC 0.51 수준(랜덤급) — 임베딩 초기화 스케일이 너무 커서 FM 항이 불안정.
  - 수정(임베딩 초기화 std=0.01, lr=3e-4, gradient clipping 추가): 안정화됨. logloss 0.685대(GBDT와 비슷한 스케일), 단일 split AUC 0.566.
- **`jh_ws/deepfm_cv.py`**: 안정화된 구조로 5-fold 진짜 group k-fold 정식 OOF 검증 → **AUC 0.56127, logloss 0.68543** (fold별 0.558~0.565). GBDT 앙상블(0.570 전후)보다 낮음 — DeepFM 단독으로는 as-of 피처 엔지니어링을 못 따라감. 다만 GPU 덕에 fold당 몇 초, 5-fold 전체 42초로 매우 빠르게 반복 가능했음.
- 전체 데이터 90%로 최종 재학습해 `pitcher_id`(792×16)/`batter_id`(830×16) 임베딩 추출, `deepfm_cv_result.pkl`로 저장.
- **`jh_ws/test_emb_catboost.py`**: 이 임베딩을 CatBoost(단일 모델, 진짜 group split)에 추가 피처(32차원 + pitcher·batter 내적 `pb_dot` 1개)로 넣었을 때 효과 검증.
  - baseline(임베딩 없음, 47피처): AUC 0.57526
  - with_emb(임베딩 33개 추가, 80피처): **AUC 0.57597, +0.00071**
